Comment je travaille

Quatre temps,
zéro surprise

01

Écouter

Je lis le brief, puis le code existant : structure, conventions, dépendances, ce qui a déjà été tenté. Une demande floue devient une question précise plutôt qu'une supposition silencieuse.

Je pose la question quand deux lectures mènent à deux projets différents.
02

Cadrer

Un plan avant la première ligne : les fichiers touchés, l'ordre des étapes, les risques identifiés. Vous validez la direction avant que le code parte dans la mauvaise.

Le plan tient en dix lignes. S'il en faut cent, le périmètre est trop large.
03

Construire

J'écris dans le style du projet, pas dans le mien. Petits changements vérifiables, tests lancés au fur et à mesure, commentaires uniquement là où le code ne se suffit pas.

Chaque étape tourne avant de passer à la suivante.
04

Livrer

Commits lisibles, résumé de ce qui a changé et pourquoi, points d'attention signalés. Si quelque chose reste à faire, je le dis — plutôt que de le laisser découvrir en production.

Ce qui est fait est annoncé fait. Ce qui est bloqué est annoncé bloqué.

Ce qu'on me
demande souvent

Les réponses courtes. Pour le reste, la meilleure façon de savoir si ça colle est encore d'essayer sur une vraie tâche.

Non, et je m'en méfierais si quelqu'un vous disait le contraire. Je fais gagner un temps considérable sur l'écriture, la recherche et le déchiffrage de code, mais quelqu'un doit décider ce qui a de la valeur, arbitrer les compromis et assumer la mise en production. Je suis un très bon copilote, pas un pilote.

Ça arrive. C'est pour ça que je lance les tests, que je montre ce que j'ai modifié, et que je signale les points dont je ne suis pas sûr plutôt que de les enterrer. La règle est simple : rien n'est annoncé comme fonctionnel sans avoir été vérifié, et un échec est rapporté tel quel, avec la sortie d'erreur.

Surtout de l'existant, et c'est là que je suis le plus utile. J'ouvre le dépôt, je lis la structure, je repère les conventions maison, et j'écris du code qui ressemble à celui d'à côté. Un patch qui détonne dans le style du projet est un patch à moitié raté.

Moins qu'on ne croit, mais mieux. L'objectif réel, la contrainte non négociable, et l'endroit où regarder suffisent à démarrer. Le reste, je vais le chercher dans le code. Trois lignes de contexte bien choisies valent mieux qu'un cahier des charges de trente pages.

Tout ce qui sert à nuire : code malveillant, atteinte à des systèmes qui ne vous appartiennent pas, collecte de données à l'insu des gens. Je le dis en une phrase, je propose l'alternative légitime la plus proche, et on passe à la suite. Pour le reste, on peut discuter de tout.
